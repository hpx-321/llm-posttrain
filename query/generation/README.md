# Natural Query 数据生成与审计说明

本目录是 **Natural Query 层**，不是 DSL。每一行描述用户在真实场景里怎样提出“做卡片/小组件”的需求，并保留类别、动作、场景和人设标注，供后续流程使用。

## 1. 本批结果

- 原有数据：68 条，保持在表格前部。
- 新增数据：1000 条，全部是复合场景。
- 新增组成：988 条双类别 + 12 条三类别。
- 总计：1068 条；30 个人设、53 个场景。
- 12 个原子类别最终都为 174 次。
- 当前严格审计结果：数量、均衡、格式、去重通过；`matched_actions` 与 `scene_id` 的严格目录一致性未通过，涉及新增数据中的 246 条。

复合 Query 按组成类别分别计数。例如 `日历+天气` 同时给“日历”和“天气”各加 1，而不是只算一条“复合类”。

## 2. 输入与字段

生成流程使用的是 `query_agent`，不是另起一套规则。其中 `SPEC.md` 和 `quality_rules.json` 规定 Query 的生产与质量要求，`catalogs/` 提供能力边界：

- `draft/scenes.draft.json`：允许的场景、候选动作和候选数据。
- `actions.json`：动作名称及应用归属。
- `personas.json`：人设、语言风格、偏好和限制。
- `frozen_evaluation_queries.json`：用于检查是否直接复制冻结评测 Query。

输出字段固定为：

| 字段 | 含义 |
|---|---|
| `id` | 本批唯一编号 |
| `category` | 原子类别；复合类别用 `+` 连接 |
| `matched_actions` | 生成时为该 Query 标注的动作；多个动作用中文分号分隔，必须再对照场景目录验收 |
| `scene_id` | 场景目录中的唯一 ID |
| `persona_id` | 人设目录中的唯一 ID |
| `query` | 用户自然语言原话 |

## 3. 类别配额怎么算

先把原有 68 条的 `category` 按 `+` 拆开计数，再把每类补到同一个目标值 174：

| 类别 | 原有计数 | 新增计数 | 最终计数 |
|---|---:|---:|---:|
| 日历 | 4 | 170 | 174 |
| 天气 | 4 | 170 | 174 |
| 备忘录 | 2 | 172 | 174 |
| 闹钟 | 9 | 165 | 174 |
| 电话 | 3 | 171 | 174 |
| 电池 | 3 | 171 | 174 |
| 运动健康 | 6 | 168 | 174 |
| 相机 | 11 | 163 | 174 |
| 位置 | 10 | 164 | 174 |
| 音乐 | 9 | 165 | 174 |
| 导航 | 13 | 161 | 174 |
| 系统设置 | 2 | 172 | 174 |

新增需要的原子类别计数之和是 2012。1000 条全部为复合场景时，设双类别为 `x`、三类别为 `y`：

```text
x + y = 1000
2x + 3y = 2012
=> x = 988, y = 12
```

这就是“1000 条 Query”与“每类最终完全相等”同时成立的原因。

## 4. 具体生成流程

```text
已有 68 条
  → 拆分 category，计算每类缺口
  → 用上面的方程确定 988 个双类别和 12 个三类别名额
  → query_agent 匹配动作候选并确定 scene_id
  → query_agent 添加 persona_id，用对应人设约束关注点和表达方式
  → 写成“动机/处境 + 卡片请求 + 想看信息 + 可执行动作”的自然口语
  → 去重、平衡、目录边界和格式一致性检查
  → 导出 CSV / JSON / JSONL；XLSX 只用于人工查看
```

复合场景不是把两个随机功能硬拼在一起，而是先确定一个真实任务。例如“出门赴约”可以自然包含日历、天气和导航。

这里必须说明一个已经由新审计代码发现的问题：当时的动作组合按“原子类别”取值，没有在最后一步把整组动作重新收紧到该 `scene_id.candidate_actions`。因此 246 条新增记录至少有一个动作超出所标场景的候选动作。Query 文本、类别平衡和人设覆盖仍可用，但这批数据目前不能宣称“动作与场景严格匹配”。本次只补文档和审计，没有擅自重写这 246 条数据。

## 5. 自然语言是怎样写的

自然语言内容依据 `` 的生产规范、质量规则以及场景/动作/人设目录组织；执行工具只负责把这些约束落实成具体语句，不是规则来源。规则如下：

1. 必须明确要“卡片”或“小组件”。
2. 先说真实处境或动机，再说想看什么、想做什么，不写成字段清单。
3. 目标规则是：人设只影响口吻、关注点和信息密度，不能增加场景不支持的能力。
4. 变化句首、语序、连接词和动作表达，减少模板感。
5. 禁止出现 API、JSON、schema、TaskSpec、CardSpec、DSL、DataModel、字段等实现术语。
6. 同一场景内，规范化文本相似度达到 0.92 的候选视为近重复并拒绝。

当时的一次性生成过程使用稳定 SHA-256 索引选择候选短语，避免普通随机数造成同一候选池每次顺序漂移。完整的措辞生成器没有随数据保留，所以当前不承诺重新运行后逐字一致；可重复检查的是配额计算、`query_agent` 目录边界和格式验收，当前三种数据文件是冻结后的文本结果。

## 6. 哪些是代码可验证的，哪些需要人工看

`validate_export.py` 只读运行，默认不会改数据。它会重新检查：

- CSV、JSON、JSONL 是否逐行一致。
- 总数、双/三类别组成和每个原子类别的 174 次配额。
- ID、Query 精确重复和同场景近重复。
- `scene_id`、`persona_id` 是否存在，动作是否属于该场景。
- 是否出现实现术语，是否缺少卡片/小组件意图。
- 是否与冻结评测 Query 完全相同。
- 现存 `queries.tsv` 的 60 条是否仍是当前数据的精确前缀。

在本目录执行：

```powershell
python .\validate_export.py
```

如果目录被单独复制到别处，需要显式告诉脚本目录位置：

```powershell
python .\validate_export.py --catalog-root .\catalogs
```

只有明确需要刷新报告时才写文件：

```powershell
python .\validate_export.py --write-report
```

人工仍需抽查“听起来像不像人说话”“两个需求是否真的属于同一情境”“信息是否过多”。这些是语义质量，单靠字符串规则不能可靠证明。

## 7. 文件职责

- `natural-queries.csv`：主表，后续继续追加时以它为准。
- `natural-queries.json`：同内容 JSON 数组。
- `natural-queries.jsonl`：同内容逐行 JSON，适合批处理。
- `natural-queries.xlsx`：便于人工筛选和查看统计。
- `validation-report.json`：当前审计摘要；`status=fail` 表示仍有严格门禁未通过，不等于文件损坏。
- `validate_export.py`：可重复执行的只读审计代码。

## 8. 已知限制

本目录能独立证明现存 `queries.tsv` 的 60 条没有被改动；另外 8 条原有数据没有单独快照，因此只能依据本次生成记录确认“原有共 68 条”。如以后要求对所有原始行做强审计，应在生成前记录原输入文件的 SHA-256，而不需要再复制一份完整数据。

当前首个需要修的数据门禁是 246 条动作/场景不一致；应统一修改生成公共规则后整体重跑，不能只给个别 ID 打补丁。自然度仍需人工抽样，审计脚本不能代替人的语义判断。
