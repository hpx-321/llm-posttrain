# 手机卡片 Query 生产规范 V2

## 1. 目标

V2 生产的 Query 应当像用户对语音助手或聊天助手说的话，同时保持事实可追踪、动作不越界、复杂度可验证。

V2 不把“复杂”理解为句子更长，而是理解为围绕同一个决定，组合更多相关信息和动作：

| 复杂度 | 信息单元 | 动作单元 | 推荐表达 |
| --- | ---: | ---: | --- |
| simple | 0-2 | 1 | 一个目标，直接说需求 |
| medium | 0-2 | 2-3 | 一个目标，带轻度场景或动机 |
| medium | 3-4 | 1 | 一个

目标，带轻度场景或动机 |
| complex | 3-4 | 2-3 | 一个目标，说明动机，并形成信息到行动的决策链 |

判定时先分别判断两个维度：信息单元达到 3 个视为信息维度较高，动作单元达到 2 个视为动作维度较高。两个维度都低为 `simple`，只有一个维度较高为 `medium`，两个维度都高为 `complex`。因此每个合法数量组合只对应一个复杂度：`2 信息 + 2 动作`和`4 信息 + 1 动作`都是 medium，`3 信息 + 2 动作`是 complex。

信息单元按用户语义计算，不按字符串数量计算。例如“深圳现在 31°”是一个信息单元，即使它包含地点和温度两个必须保留的词。

## 2. 生产流程

每次生成分为以下阶段：

1. Catalog 构建（可选）：从审核场景选择主题，按阶段解析动作和数据，并绑定人设。
2. 语义规划：根据优先级选择满足复杂度数量要求的信息和动作。
3. 用户化表达：根据人物口吻、使用状态和表达样例，把规划改写成自然 Query。

生成结果必须同时返回 `query_plan`、`detailed_query` 和 `compact_query`。质量门禁根据 `query_plan` 验证自然语言，不能只相信模型的自检结果。

## 3. 输入职责

- `scene` 只描述用户要解决的问题、触发时机和真实动机，不要求逐字复制。
- `voice_profile` 只控制说法，不得提供新的事实或能力。
- `facts` 是可选择的信息单元。每项通过 `required_terms` 声明必须在 Query 中出现的原文。
- `actions` 是唯一动作白名单。每项通过 `required_terms` 声明可校验的用户表达。
- `generation` 明确本次复杂度和目标数量，不从句子长度猜测。
- `constraints` 只放硬约束，不再提供“背景全文必须保留”能力。
- `catalog_context` 标记审核场景、人设、阶段和目录版本；出现时，所有 facts/actions 必须带 `catalog_ref`。
- `catalog_ref` 使用应用 ID、正式能力名称和阶段追踪来源；一期输入禁止引用二期能力。

## 4. 用户口吻规则

自然表达优先遵循以下结构，但不固定句式：

`真实动机或使用状态 + 创建卡片的请求 + 想确认的信息 + 希望直接执行的动作`

要求：

- 使用生活语言，不出现字段名、接口名、场景 ID 或测试术语。
- 可以保留轻微情绪，例如“有点担心”“赶时间”“总拿不准”，但只能来自输入。
- 详细版通常一到两句话；精简版保留同一目标、所选事实和动作。
- 同一批次要变化开头、语序和连接词。
- 禁止使用“关键信息：A、B、C”“数据包括”等清单式表达。
- 禁止为了复杂度拼接不相关应用或动作。

## 5. 硬质量门禁

以下情况判定失败：

- 缺少卡片或小组件创建意图。
- 规划的信息或动作数量不符合目标复杂度。
- 必选信息未被规划，或所选信息的 `required_terms` 未出现在两个版本中。
- 输出包含动作白名单以外的动作，或命中禁止动作/短语。
- Catalog 输入引用不存在的场景、人设、应用或能力，或一期输入引用二期能力。
- 详细版与精简版完全相同，或精简版反而更长。
- detailed 超过输入规定长度。
- medium/complex 的详细版没有体现输入提供的动机词。
- 使用字段清单式模板，或与冻结评测集完全重复。

批量生产还会检查完全重复、近似重复和高频相同开头。

## 6. 设计取舍

V2 有意取消以下旧式约束：

- 不要求复述完整背景。
- 不把一个复合事实拆成多个字符串来凑复杂度。
- 不用 `style_applied` 声称“已经应用风格”，而是通过实际句子和证据映射验证。
- 本地生成器不再使用单一固定模板，而是先规划、再按 request_id 稳定选择表达结构。

## 7. 选型 v2（选型层，2026-08-21）

生产引擎之上增加集合层能力，覆盖“选什么、配额多少、怎么统计”：

- `selection_engine.py`：从 73 个支持场景 + 同应用能力补漏构建候选池（含复合场景对），按
  **覆盖第一**（26 动作 + 89 可见数据 100%）、难度配额（simple/medium/complex = 5/25/20）、
  尺寸配额（2x2×30 / 2x4×20，软约束）、数据指纹去重（Jaccard 惩罚）选型；产出带标注选型集
  `selection.v2.json` 与 V2 批次输入 `selection.v2.batch.json`。
- 难度标注直接复用 `classify_complexity`（信息单元 × 动作单元），不做第二套标准。
- `report_query_stats.py`：扇形图（难度/尺寸/动作类型/数据用途）+ xlsx（选型集明细、难度×尺寸、
  能力覆盖），输出 `selection.v2.report.png` / `.xlsx`。
- 双口径：`catalogs/data_usage.json`（数据用途）与 `catalogs/widget_capability_map.json`
  （7.0 ↔ widget_service）为选型与统计提供标注；选型集标注“可生成/仅表达”，TaskSpec 阶段按
  widget_service 过滤。
- 冻结评测集已淘汰（2026-08-21 决策），不再作为比对基准；`avoid_frozen_exact_match` 默认关闭。
- `quality_rules.json` 升级 2.2.0：新增 `naturalness.technical_terms` 专业词黑名单
  （API/JSON/TaskSpec/query_plan 等），`validate_result` 检出即报错。
